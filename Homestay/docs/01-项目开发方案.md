## 〇、需求审查意见(先说明,不改变核心定位)

需求整体非常完整、自洽。个别点提请注意,均按"方案中已给结论"处理:

1. **住宿业务归属模糊**(用户流程中民宿业务缺"订单管理"):以"用户端只预订、商家端管订单、履约操作在商家侧"为准(唯一例外:模拟支付超时可自助取消,恢复库存)。核心闭环不受影响。
2. **评价门槛**:除"完成后评价",再允许"已入住/已完成订单可评价",避免演示中"今日下单无法评价"的尴尬。
3. **简化与约束**:
   - 不引入 Spring Security,JWT 用拦截器 + 注解实现(权限点足够清晰、毕业设计更容易讲清,且规避 Security 与放行规则摩擦);BCrypt 密码加密、统一异常、统一返回均保留。
   - 封面图等图片统一为 URL 存储,不落盘传文件(避免部署路径问题),演示图片走稳定的站外图源 + 站内兜底方案。
   - 明确不做:真实支付、IM、AI、导航、会员、积分、优惠券、直播、分销等。

## 一、项目定位

**一句话**:以旅游民宿预订为核心,以目的地旅游资源关联 + 个人旅行计划为特色,面向"游客 / 民宿商家 / 平台管理员"的毕业设计级旅游民宿综合服务平台。

- 不做大型电商/OTA:不接真实支付、不做复杂营销与物流、不追求功能堆砌。
- 做好:民宿预订闭环 + 旅游资源关联 + 旅行计划 + 可解释推荐 + 经营/平台统计 + 三端完整 UI。
- 三端分离:用户端(C 端,旅游网站感)、商家端、管理员端(后台感)。

## 三、用户角色与权限

只保留三个角色(USER 用户 / MERCHANT 商家 / ADMIN 管理员):

| 角色 | 核心权限 |
|---|---|
| USER | 浏览全部旅游内容与已上架民宿;预订→模拟支付;收藏(民宿/景点/体验/餐饮);创建与管理旅行计划(含加入民宿/景点/体验/餐饮);已入住/已完成订单评价;举报民宿/评价/体验/餐饮;个人中心 |
| MERCHANT | 商家资料;民宿信息与图片管理;房型/房间/价格/库存管理;订单管理(接单/入住/离店/完成、取消恢复库存);查看并回复评价;经营统计 |
| ADMIN | 用户管理;商家审核(注册/商家资料需审核通过方可经营);民宿审核(上架前审核);民宿/房型/订单监管;景点/体验/餐饮资源 CRUD 与审核;评价管理(可删除违规);举报处理;平台数据统计 |

- 端隔离由登录后按角色跳转 + 前端路由守卫实现;接口级权限由后端 JWT 拦截器 + @RequireRole 校验(USER 访问商家接口被拒、商家不能改别人民宿——按 merchantId/userId 归属校验)。
- 默认账号:admin / 商家 / 用户(见初始化数据,密码统一 123456)。

## 五、业务流程

### 5.1 游客→用户 核心预订闭环

```
浏览首页/目的地 → 选大理 → 民宿列表(按推荐分/筛选排序)
→ 民宿详情(房型日历/周边"住这里玩什么吃什么")
→ 选房型+日期 → 订单确认(房费试算=天数×单价×间数)
→ 下单(校验库存,双表防超卖) → 模拟支付(微信/支付宝/银行卡) → 已支付
→ (商家后台处理) 待入住 → 入住中 → 离店完成 → 评价(五维评分+图文)
```

- 待支付 15 分钟未付 → 自动取消并恢复库存(演示时提供手动取消)。
- 取消/拒单均恢复库存;已完成/入住中的订单不可取消。

### 5.2 民宿×旅游资源关联(创新点①)

```
商家/管理员 在民宿编辑页维护"周边景点/体验/餐饮"关联(多对多)
用户浏览民宿详情时聚合展示:住这里 → 周边景点 | 周边体验 | 周边餐饮 三类卡片
```

### 5.3 个人旅行计划(创新点②)

```
用户:新建计划(名称/目的地/起止日期/简介)
→ 从民宿/景点/体验/餐饮任一资源详情页"加入旅行计划"(选计划+第几天+时间)
→ 计划详情按天分组展示;可增删项目、调整顺序、删除计划、标记完成
```

### 5.4 民宿推荐(创新点③)

```
推荐分 = 综合评分40% + 价格匹配20% + 距离匹配20% + 热度10% + 偏好匹配10%
```

- 距离匹配:以用户当前定位城市/目的地或默认大理为"参考点",按民宿经纬度算距离得分;
- 偏好匹配:用户收藏过的资源类型/目的地 → 偏好标签(无偏好则该项取中性分);
- 列表页/推荐接口返回 factors(各因子得分与说明),前端解释"为什么推荐你"。
- 未登录游客有默认参考点,同样可推荐。

### 5.5 商家/管理员统计

- 商家:今日订单/本月订单/本月收入/入住率/平均评分 + 近7天订单趋势、月度收入趋势、房型销量排行、订单状态分布(ECharts)。
- 管理员:用户/商家/民宿/订单总量、本月交易额、待审核数 + 用户增长、订单趋势、收入趋势、热门目的地/民宿、订单状态分布。

## 六、数据库设计

### 6.1 设计约定

- MySQL 8、InnoDB、utf8mb4;主键 BIGINT 自增;所有表含 create_time / update_time / deleted(逻辑删除,默认 0)。
- 索引设计:外键列、查询条件列(目的地/状态/类型/用户/商家/日期)建普通索引;预订唯一约束见房型库存。
- 金额 DECIMAL(10,2),经纬度 DECIMAL(10,6);状态一律明确枚举字符串 + 常量类。
- 逻辑外键 + 索引(物理外键会让初始化与删除复杂;论文中说明"逻辑外键 + 应用层约束"保证第三范式)。

## 七、后端架构

```
backend(Java 17 / Spring Boot 3.2.x / MyBatis-Plus / Maven / Lombok / Jakarta Validation / JWT / BCrypt)
└─ src/main/java/com/tourism/
   ├─ TourismApplication.java
   ├─ common       Result/常量/PageVO/异常(BizException、GlobalExceptionHandler)
   ├─ config       拦截器、MP 分页与自动填充、WebMvc、CORS、Jackson、静态资源映射
   ├─ security     JwtUtil、JwtInterceptor、@RequireRole、LoginUser(ThreadLocal)
   ├─ controller/service/service.impl/mapper/entity/dto/vo  按域分包
   └─ resources    application.yml + sql/schema.sql、data.sql
```

- 统一返回 Result<T>{code,msg,data};统一异常处理 GlobalExceptionHandler;业务异常 BizException。
- 参数校验 Jakarta Validation(分组新增/修改);分页统一 PageVO<T>。
- BCrypt 密码;登录签发 JWT(userId+role),拦截器校验,401 由前端统一跳登录。
- 下单防超卖:room_inventory 行锁 + 唯一约束兜底。
- 图片:本地上传目录(uploads/,静态映射)与稳定外链 URL 并存;初始化数据默认稳定外链。

5. 商家视角:订单/入住率/收入图表;
6. 管理员视角:平台统计、审核(待审核商家/民宿)、举报处理、资源/评价管理。
